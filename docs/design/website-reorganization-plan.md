# 网站整理方案（待批准，尚未实施）

日期：2026-11-24。范围：网站功能、人员与权限、项目目录、历史代码与发布流程。

本轮只检查代码、读取当前配置数据库并制定方案；没有修改业务数据、账号、菜单或线上服务。本文中的目录和菜单是目标设计，不表示已经迁移。数据库检查使用只读事务；日志覆盖和表行数都不能单独证明一个功能无人使用。

## 一、我的决定

把网站整理成以直播运营为主的工作系统：保留现有客户、挽单转推、运费、主播和礼品业务；合并重复入口和重复配置；旧 ERP、财务、DataHub 继续退出日常网站；先归档历史实现和发布包，第一轮不删除历史业务表。

这次以“可完整构建、人员配置清楚、入口统一”为完成标准。先建立可靠基线，再清理代码。暂不把 `xinke-erp` 改名，也不同时更换技术框架、重写客户中心或重做主播 App。

## 四、人员管理设计

### 1. 一个人员入口，看清四件事

列表显示：姓名、账号、部门、账号状态、业务岗位、关联店铺/直播间、人员组、权限异常标记。详情分为“基本资料、业务分配、实际权限、变更记录”。手机号等个人信息仅按现有管理权限展示，不进入公开的整理报告。

把以下概念明确区分：账号决定能否登录；部门表达组织关系；业务岗位表达在哪家店或哪个直播间做什么；权限决定能打开哪些页面、执行哪些操作、看到哪些数据。

基础权限逻辑：**有效账号 + 有效业务分配 + 授权规则 → 页面和必要操作权限；业务数据范围仍由服务端检查。** 菜单可见不能代替接口鉴权或订单范围校验。

“主播/场控/客服”优先作为业务岗位配置，避免为了选一个主播又单独维护一遍系统角色。已有 `sys_post` 不直接删除；确认其引用后，普通管理员不再需要进入单独岗位页面重复维护。

### 2. 店铺人员组作为默认配置方式

- 根据现有两套不同的客服与管理员名单，生成两组待迁移方案；组名按实际业务用途确定，不凭人员姓名推断业务归属。
- 分组迁移前后逐店比较有效名单，第一批迁移必须保持人员、岗位及当前数据范围一致。
- 同一组绑定多家店铺：新增、移除客服时维护一次；保存前显示受影响的店铺和人员。
- 个别店铺确需不同名单时，选择“单独配置”。第一版不引入多层组继承或多组叠加，减少权限来源不清的问题。
- 从组中移出店铺时，默认保留当前有效名单并转换为单独配置；切换到另一组时预览将被替换的名单。
- 停用店铺保留配置用于审计，但不再触发自动业务授权。

### 3. 自动授权与历史授权合并治理

- 配置客服或客服管理员后，按规则自动开通挽单与转推中心、运费等对应能力；主播/场控按已确认的业务规则获得 App 上报及对应业务入口。
- 先排查“9 人符合条件、挽单自动角色 0 人”的原因，核对迁移版本、线上代码、任务状态、规则和权限缓存，再修复。不能只补几条 `sys_user_role` 掩盖问题。
- 权限详情显示授权来源：业务分配自动获得、系统角色、管理员特殊授权，并显示对应数据范围。
- 以手机号命名的专用角色先映射实际权限和用途；普通业务访问迁移到岗位规则，确有特殊用途的保留为有原因的特殊授权。只有迁移核对通过且没有依赖后，才退役旧角色。
- 无成员角色先检查定时任务、规则、接口及代码引用。自动角色即使暂时没有成员也不等于无用；`adminss` 等无成员人工角色作为退役候选，不直接批量删除。
- 移除最后一项有效业务分配时，撤销该分配产生的自动权限；仍有其他来源时明确显示，避免看似撤销但实际仍可访问。
- 京东客户信息延续此前“所有正常登录用户可用”的业务要求，不在整理过程中擅自收窄。管理员操作仍按实际接口规则单独核对。

### 4. 账号停用和钉钉同步

- 不按最近登录时间自动删人、停人，也不自动合并同名账号。无登录日期、无角色的账号进入核查视图。
- 停用前显示待跟进客户、未完成挽单、主播分配及其他业务责任；管理员选择交接对象或记录暂不交接原因。
- 停用后终止可登录会话、阻止新的业务分配和操作；保留历史订单负责人、记录姓名快照和审计信息。交接只调整指定待办，不改写历史业绩。
- 对已发现的停用场控映射给出具体核查单；第一轮不自动给未知人员改派工作。
- 当前钉钉同步会按来源写账号状态，绑定用户更新还会写 `del_flag='0'`；需增加“组织来源状态”和“本地管理停用”边界，防止本地停用/删除被下一次同步覆盖。
- 钉钉负责组织与基础资料；业务分组、权限和本地停用策略由网站负责。同步结果展示新增、资料变更、来源缺失及失败原因；来源不完整时不据此批量停用。

## 五、功能去留

### 保留并整理

直播客户中心及独立评论采集插件、京东客户/RPA 导入、挽单转推、运费征收及看板、主播 App/上报/分配/区间与修正记录、礼品登记/库存/成本/快捷模板、相关 BI 事实与同步任务、钉钉同步、必要通知与提醒、审计日志和 App 更新功能。

京东当前数据为空、人员组当前为空，都不作为删除理由：前者是新业务，后者正好用于解决重复配置。

### 合并入口与实现

礼品登记/台账/汇总收敛到工作台标签；礼品目录/库存/成本归入物料配置；人员、店铺、直播间配置从大型礼品管理实现中拆出独立服务和页面。拆分按接口契约逐步进行，第一轮不改变业务字段含义。

### 退出日常使用并归档

旧观众客户页面、旧客户工作台、旧主播 DOM 上报插件及配套旧启动器、重复发布脚本、过时安装教程、历史安装包。先检查调用和发布入口，再停止分发，旧接口保留一个发布过渡期。直播评论/客户插件不属于旧主播插件，继续保留维护。

旧 ERP、财务、采购、DataHub 不恢复菜单；保留相关历史数据。`erp_shop`、礼品表、主播和挽单 BI 表等仍被当前业务依赖的对象属于现用资产，绝不能按 `erp_`、`bi_` 前缀清理。

### 生产环境移除开发工具

表单构建、代码生成器、Swagger 工具菜单退出生产日常导航；代码生成模块改为开发环境可选，生产运行包不再默认依赖。接口文档如开发联调仍需使用，限制在开发配置中。服务监控、日志和必要字典保留为管理员功能。

隐藏菜单、封闭接口、移除运行依赖分别验证，不能只隐藏前端就认为功能已下线。

## 六、目录和代码整理

保留现有 Maven 模块边界，减少一次变更的兼容风险。目标职责如下：

```text
xinke-admin/             启动入口、系统控制器、运行配置
xinke-framework/         鉴权、安全、拦截器与基础框架
xinke-system/            账号、组织、角色和基础管理
xinke-common/            通用代码
xinke-erp/               现有业务模块，内部按客户/挽单/运费/主播/礼品/配置划分职责
xinke-ui/                网站主入口和共享组件；保留 App 本地界面构建目标
clients/
  anchor-metrics-probe/  当前主播桌面 App
  extensions/douyin-live-customer-v2/  当前直播客户采集插件
config/
  local/                本机私有配置（不进入版本库）
  database/             迁移入口说明、有效迁移与历史 SQL 分类
scripts/
  server/               统一构建、检查、部署、回退入口
  client/               客户端打包入口（核对引用后归并）
docs/
  design/               设计与决策
  user/                 网站/App/插件使用文档
  operations/           环境、发布、备份与回退
```

处理原则：

1. 建立文件清单，区分源码、配置、构建物、历史产物、恢复备份和密钥。`.codex-deploy` 混有线上基底、备份及私有材料，必须逐项分类，不能整目录删除。
2. 根目录压缩包、旧安装包与已核对的历史构建物移到工作区外的归档目录，建立版本、日期、用途、校验值索引；备份和密钥采用对应的受限存放位置。
3. `target`、`dist`、临时日志和缓存按构建脚本引用核实后清理并规范忽略规则；发布脚本仍依赖的文件先解除依赖。
4. 历史 SQL 分为可用迁移、旧版本参考和禁止直接重跑的初始化/清理脚本；补齐执行次序与迁移记录，不用旧整库脚本做本次整理。
5. 旧路由收敛到兼容路由清单；先保留重定向，检查动态菜单、独立页面、插件与 App 调用后再移除旧实现。
6. 清理前端依赖以实际导入、动态组件、构建插件和样式使用为依据，不能仅凭文件名或页面无菜单判定无用。
7. 当前工作区先做完整可恢复快照并建立基准。所有整理作为新的、可单独比较的变更保存，不覆盖已有未提交成果。

## 七、实施顺序与放行条件

### 第一批：建立可恢复、可复现基线

核对本地源码与线上 JAR/UI/菜单/数据库版本；备份数据库、网站资源和后端产物，验证至少一次恢复到测试环境。区分数据备份与程序回退：程序回退不能拿旧数据库覆盖上线后新增业务数据。

补齐本地缺失或与线上不同的当前功能，实现一条可完整构建的发布路径。记录版本、源码快照、迁移列表、产物校验值与运行配置需求。测试环境使用与生产隔离的数据库/Redis/任务配置，避免发送真实提醒、运行真实同步或影响生产采集。

交付：版本差异清单、有效文件/功能依赖清单、可恢复基线、可从源码生成的完整测试版本。没有通过这一步，不开始大规模删代码或全量覆盖线上。

### 第二批：入口与人员配置

统一主站入口和布局；接入共享人员组；增加人员业务分配与实际权限详情；修复自动授权一致性；明确钉钉同步边界。分组迁移必须出具逐店名单差异，保持当前有效配置。

交付：上述目标菜单、人员管理与店铺组页面、授权来源核对、旧入口兼容、关键操作日志。对实际人员停用、特殊权限扩大或缩小、订单改派，输出逐项处理清单；不凭整理规则批量决定人员去留。

### 第三批：内部拆分与历史归档

把人员/店铺/直播间配置从礼品模块的混合实现中逐步拆出；合并重复组件/API/构建入口；退役开发工具生产依赖；停止分发旧主播插件；归档经核实的旧源码、产物和脚本；更新 README 与使用文档。

交付：代码与目录职责清楚、历史文件可追溯、构建脚本不再依赖混杂的临时目录、当前 App 与客户插件保持兼容。

### 第四批：完整回归后发布

- 主站完整构建、相关后端测试通过；新空目录按文档可生成完整产物。
- 管理员、客服、客服管理员、主播/场控、普通用户和停用用户的菜单/接口/数据范围分别验证；特殊授权和多店铺移除验证。
- 人员组更新、切换、解除和停用店铺验证；迁移前后有效名单与授权来源可比较；权限缓存与重新登录行为验证。
- 直播客户插件接收、领取、跟进、转交；京东导入拆单/重复处理/联系方式复用；挽单与转推、运费重复单拒绝和快速录入保持正常。
- 主播 App 登录、数据上传、分配、交接、区间计算和修正保持正常；App 下载/更新签名、旧版协议兼容验证。若本批调整安装包，再补无开发环境电脑安装验证。
- 礼品登记、库存流水、导出与业务看板核对；关键指标与迁移前同一数据集比较。
- 旧地址和旧客户端兼容；增量迁移可重跑，回退演练完成，历史记录与附件可访问。

测试通过后按批发布，保留上一版程序及资源，执行上线冒烟检查。涉及数据库结构的步骤优先做向后兼容的增量变更。

## 八、本次同意后的实施边界

同意本方案后，实施以上四批网站整理：基线核对与备份、功能入口合并、共享人员配置、权限治理、确认无依赖的历史代码归档、完整测试和分批发布。

第一轮不删除历史业务表、历史客户/订单/附件，不硬删除账号，不按未登录自动停用人员，不自动改派待办，不凭名称删除角色，不自动发布新的 App 安装版本。需要改变具体人员去留或特殊授权的项目，以核查结果形成独立的具体处置清单。

当前仍待实施阶段确认：线上与本地完整差异、旧接口实际调用方、自动角色不一致原因、历史角色的实际权限来源、当前人员分组业务名称、无菜单历史功能的外部引用。它们都有核对路径，不阻碍先建立基线，也不以猜测代替验证。
