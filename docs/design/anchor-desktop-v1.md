# 鑫客主播工作台 App 改版方案

状态：待确认的设计；2026-11-24。本轮不修改业务代码、不迁移数据库、不发布版本。

## 目标与边界

将主播数据采集、上报、记录查看和直播间主播分配集中到 App。网站继续作为同一份数据的查看、管理入口。此次迁移针对主播上报插件；评论监听助手是独立业务，不在此次替换范围内。

建议下一版命名“鑫客主播工作台”，版本暂定 0.3.0。先完成 App 上传到服务器、网站查询同一条记录的验证，再停止主播上报插件入口，避免两个入口同时误报。旧历史记录保留。

## 页面与视觉

沿用现有网页：浅灰底、白色内容区、深色文字、橙色主操作、细分隔线、紧凑表格。左侧导航为“上报工作台 / 上报记录 / 主播分配 / 设置与更新”。默认窗口约 1320×840，支持窗口缩放。

顶部常驻当前网站账号、百应登录状态和更新提示。网站账号用于权限及操作留痕，百应账号用于获取平台数据；两者分别登录、分别退出。网站退出后不能上传，百应退出后仍可查看服务器历史记录。百应页面只在登录、授权失效或排障时显示。

### 上报工作台

1. 显示接口 nickname 作为直播间名；直播标题、开播时间、平台场次 ID 分开呈现。
2. 默认最新可打开场次，其他场次使用“切换场次”弹窗；以平台场次 ID 区分，不靠标题识别。
3. 显示对应系统直播间。无法匹配或同名有歧义时阻止上传；有管理权限的人明确绑定，不能猜测。
4. 主区显示当前整场累计指标、采集时间、完整性状态；上次上报时间和主播在右侧。
5. 本次主播下拉框只列出当前直播间已分配的有效用户。网站登录用户本身在名单中时默认本人，否则要求选择；不默认名单第一人，不把登录操作员自动当成主播。
6. 提交前生成区间预览，醒目标注“本次归属主播”、开始和结束时间，区分整场累计与区间增量。
7. 主按钮“采集并预览本次上报”先重新取本场数据，再请求服务器预览；用户核对后点击“确认上报”。可单独手动刷新；不按秒持续刷新。
8. 成功后显示服务器记录编号，刷新上次上报和本场记录，网站立即查询到同一条记录。

九项核心指标加成交金额为自动上报完整性门槛。含异常交易金额只作参考。互动人数由累计观看人数×观看互动率估算，必须明确标识。比例、金额单位沿用现有服务端约定。区间比例由服务器按原规则计算，不直接相减两个百分比。

采集时间就是本次自动上报的结束时间，不能拿当前数据填写过去某个结束时间。刷新或切换场次后，旧预览失效，需重新生成。

### 上报区间规则

- 有上次记录：本次从上次结束时间接续，提交上次快照版本/ID，由服务端锁定场次并校验。
- 第一条记录：沿用现有规则从本场开播接续。若实际只负责后半段，不能直接把之前累计算给自己，须先由管理人员补录前段或设置明确、可审计的起始快照。
- 不提供“自动推断谁上播了”的功能，也不因采集成功直接上传。
- 缺项、账号失效、房间未匹配、主播未分配、数据倒退、预览过期均阻止正常提交，给出对应解决入口。
- 金额退款或累计指标修正导致负差值时进入待核对，不静默归零。
- 两台电脑同时提交：服务端冲突时展示“已有新上报”，重新读取区间；不能把旧预览强行写入。
- 连续点击/超时重试复用同一幂等键。网络失败保存本地待确认草稿，恢复后先核对服务器是否已成功；不自动把旧快照当新快照上传。

### 上报记录

沿用网页“直播间 → 场次 → 主播区间”结构。支持今天、近7天、近30天、自定义日期。表格包含开播时间、主播、区间、时长、来源和区间经营数据。可展开查看采集快照和操作记录。

管理账号具备“新增补录 / 调整 / 作废”；复用现有连续区间补录、相邻记录重算、原因必填、版本冲突校验。保存前列出受影响记录，历史操作留痕。普通上报人员查看有权限的记录，不显示管理按钮。App 与网页的数据来源标签统一增加“App上报”，原“插件上报”历史来源不变。

### 主播分配

直播间列表展示名称、已分配主播和人数。选择直播间后，可搜索系统有效用户，勾选并保存，可一直播间多主播、一主播多直播间。支持将一间的名单复制至另一间；预览新增和移除项后保存，不静默覆盖。

分配只改变候选主播名单，不等于给某人新增已上播时段。移除主播不删除历史上报。分配后刷新 App 和网站同一份关系。被分配账号可获得该模块必要的访问/上报能力，不自动取得分配、调整、作废等管理权限。数据范围与主播归属由服务端校验。

### 设置与更新

包含网站登录、百应登录/退出、运行日志、当前版本、检查更新。日志可按“采集 / 上传 / 登录 / 更新”筛选，默认不展示 Cookie 或完整带令牌 URL。出现错误时给出具体原因、请求对应场次和可执行操作。

更新不在采集、上传、编辑未保存时强制执行；先提示，允许稍后安装。下载与校验失败不启动安装，继续使用当前版本。覆盖安装保留登录目录和本地草稿；本机缓存结构变更必须有版本迁移。

## 权限与接口设计

现有代码：网页通过 `/live/metrics/rooms`、场次详情、主播增删和区间管理接口工作；分配/补录/调整/作废目前要求 `live:metrics:manage`。已有上报 v3 使用匿名插件接口和共享 key，记录来源及操作人硬编码为 PLUGIN/plugin。

新版建议新增需要网站登录令牌的 App 上报上下文、预览、提交接口，共用 LiveHandoverService 的事务、计算、幂等和 BI 事件逻辑；不要直接把匿名插件接口换一个客户端名称继续使用。提交人由服务器登录态获取，不能由 App 随意填写。

普通上报权限单独设计为 `live:metrics:report`，分配及历史管理继续要求 `live:metrics:manage`；具体直播间范围也须在服务端校验。页面隐藏按钮只是体验，不能代替接口检查。现有全登录可查的接口需要同步明确记录与人员候选列表的数据范围。

关键字段：source=APP、operatorUserId、anchorUserId、clientVersion、platformSessionId（字符串）、roomId、previousSnapshotId、capturedAt、idempotencyKey、原始累计快照及计算版本。是否已有相应字段需实现时核对迁移；不另建一套与网页割裂的业务事实表。区间预览签名/版本与提交使用同一份快照，防止预览后变更归属或边界。

身份识别先复用现有房间关系，名字只用于初次匹配/核对；平台账号标识如后续取到应保存明确映射。不能把不同账号下相同标题当成同一直播间。

App 建议保留 .NET/WebView2 安装外壳，业务界面使用本地打包的 Vue + Element Plus，复用网站的样式和组件。采集专用 WebView 与业务界面隔离，只传递经校验的房间、快照数据。百应登录凭据留在本机，不上传到服务器。网站令牌使用系统保护存储；现网入口为 HTTP，新增正式账号登录前需落实 HTTPS。

## 通过网站发布 0.3.0 的流程

现有 0.2.13 已具备 `/anchor-app/latest.json` 签名清单检查、签名校验、安装包 SHA-256 校验、下载并启动安装程序的基础，可直接作为首次网站更新的起点。

1. 完成新版功能与服务端兼容接口，先测试数据库与接口，部署服务端。
2. 在发布电脑构建 0.3.0 安装包及签名清单；私钥继续保存在发布电脑。
3. 网站新增“软件更新”管理页：版本、说明、安装包、签名清单、下载地址、草稿/已发布/已撤回。仅授权管理人员可发布。
4. 上传安装包和签名清单，服务器校验版本、文件摘要和签名；校验通过才能发布。先使安装包可下载，再原子切换最新清单。
5. 先在一台已有 0.2.13 的电脑点击“检查更新”，按现有提示下载安装 0.3.0；验证版本、登录保持、自动采集、上传及网站记录。
6. 通过后再开放推广，旧版 App 无需手工寻找桌面安装包。

本次用户已表示希望尝试网站更新；本轮只定设计，功能实现和测试后再实际发布。更新网站无须为静态安装包分发重启业务服务。普通网站前端更新需保留 `/anchor-app/` 发布目录。

撤回发布只影响尚未升级的客户端。现有升级器不支持自动降版本；已升级客户端出现问题时发布更高版本修复，或提供旧安装包人工恢复，不把“撤回”设计成已安装用户的自动回滚。

## 验收

- 用已登录百应读取九项与成交金额，按 nickname 显示直播间，标题与场次正确。
- 普通账号选已分配主播，上报一条区间，网站显示同一条记录及 App 来源、操作人。
- 分配/移除一名主播，App 与网页同步；历史记录不受影响，未授权账号不能修改。
- 两台设备并发、重复点击、提交超时、Cookie 失效、网站令牌失效、缺项、累计倒退均给出正确行为。
- 补录、调整、作废能正确重算相邻区间，BI 仍走现有变更流程。
- 从 0.2.13 经网站升级到新版，安装前保护未保存内容，覆盖后保留登录状态，网站显示上传结果。

交互预览里的人员、区间和更新状态均为示例，仅用于评审布局和流程。
